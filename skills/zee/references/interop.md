# Skill & Tool Interoperability (`zee`)

`zee` stays 100% self-contained and never hardcodes third-party skills, packages, or machine-specific paths. It interoperates with whatever skills and project tools exist in the active harness through three strict boundaries.

## 1. Boundary of Three Skill Classes

1. **Domain & Craft Skills** (e.g., frontend craft, framework guides, security checklists, benchmarking):
   - Discovered natively from the active host's `<available_skills>` prompt list.
   - Orchestrator checks `<available_skills>` once during Intake/Design; if a skill clearly matches a unit, pass its exact absolute `location` path to the worker via the Worker Brief (`Optional Reference Skill: <absolute-path>`).
2. **Project Commands & Checks**:
   - Declared per repository in `<repo>/.agents/zee.project.json` (`testCmds`, `lintCmds`, `uiCheckCmds`, `riskPaths`, `uiGlobs`, `denyCommands`).
   - `Scout` verifies these commands against repo build manifests; `UI`, `Coder`, and `Verifier` execute them directly rather than hardcoding global tool paths.
3. **Competing Orchestrators / Workflow Controllers**:
   - Never invoked inside `zee` subagents.
   - Every Worker Brief starts with `[zee-worker]` and `worker.md` (`Direct Execution Only`). On Pi, `zee_subagent` also spawns workers with `-ne` (`--no-extensions`) and `ZEE_WORKER=1`.

## 2. Artifact Interop

- All `zee` handoff files (`SPEC.md`, `plan.md`, `DESIGN.md`, `<busDir>/context.md`, `<busDir>/ui-spec.md`, `state.json`, `decisions.tsv`) are standard Markdown, JSON, and TSV.
- Approved plans generated by `/zee-plan` (or external planning tools) can be passed directly to `/zee` or `/zee-night` via the Approved Plan Fast-Path without re-interviewing.
